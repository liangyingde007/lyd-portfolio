01 / CONTEXT

一笔订单，三个并发问题。

订单会依次经过凭证校验、订单保存、库存锁定和支付状态更新。重复点击与重复通知，会在不同步骤产生不同的问题。

  1. SUBMIT

    提交订单

    同一个 Token 能否被多个请求消费？

  2. INVENTORY

    锁定库存

    可用库存是否满足本次锁定？

  3. PAYMENT

    支付回调

    已支付的订单能否再次迁移状态？

实践重点

  • 梳理订单确认、提交、库存锁定与支付回调的调用关系。
  • 分析 Token 原子消费、订单状态条件迁移与多 SKU 库存锁定。
  • 将关键链路整理成代码说明和技术文章，继续讨论异常与边界场景。

项目包含商品、购物车、订单、库存和秒杀等模块。本案例聚焦交易链路，基于已有商城工程进行实践与优化。

02 / TOKEN

同一个 Token，只消费一次。

用户进入确认订单页取得 Token。多次点击提交时，多个请求可能携带相同 Token；如果校验和删除分成两步，它们可能同时读到有效值。

选择

用 Lua 在 Redis 内原子完成取值、比较与删除，减少校验和删除之间的并发窗口。

实现

submitOrder() 传入用户的 Token key 与请求 Token。仅匹配时删除；返回 0 的请求按防重校验失败处理。

实现片段Lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end

设计边界

这一步限制 Token 的重复消费。客户端超时、服务失败、订单已落库后的重试仍需结合业务请求标识与数据库约束处理。

03 / STATE TRANSITION

把状态判断，放进更新条件。

支付成功通知可能重复到达。将订单号与「待付款」一起作为更新条件，仅在预期状态下迁移为「待发货」。

handleOrderComplete() 调用 markPaidIfPending()，通过受影响行数判断是否首次迁移。数据库在一次更新中完成状态判断与修改。

实现片段MySQL
UPDATE oms_order
SET status = #{targetStatus}, modify_time = NOW()
WHERE order_sn = #{orderSn}
  AND status = #{expectedStatus};

设计边界

影响行数为 0 并不只表示重复回调，也可能是订单不存在或状态不匹配。库存、购物车与积分等后续动作仍需完善，状态迁移的幂等不能自动覆盖这些动作。

04 / INVENTORY

按一致顺序锁定，
在更新时检查库存。

两个订单包含相同 SKU、却以相反顺序提交时，会增加相互等待的可能。读取库存后，其他事务也可能改变可用数量。

固定 SKU 顺序

orderLockStock() 先按 skuId 排序，再逐个尝试锁定库存。

使用条件更新

更新 stock_locked 前检查可用库存，以受影响行数判断本次锁定是否成功。

实现片段MySQL
UPDATE wms_ware_sku
SET stock_locked = stock_locked + #{count}
WHERE sku_id = #{skuId}
  AND ware_id = #{wareId}
  AND stock - stock_locked >= #{count};

这里增加的是锁定库存，支付后的实际出库扣减属于另一业务步骤。

设计边界

固定 SKU 顺序只控制一个维度。仓库访问顺序、跨服务事务和失败补偿，需要结合完整运行场景验证；目前没有并发吞吐或死锁发生率的实测结论。
